# Phase 5 — UI

Goal: five screens that make the data usable. Can start once phase 2
lands; the run screens need phase 3.

**Status: done.** All five screens ship, with one documented deviation: the
import screen has no credentials form, because phase 4 decided an instance
import is a CLI job and there is no route to start one (section 2, Import,
below).

Every console screen lives in the `app/(console)/` route group, which holds
the session check once so a screen added later cannot forget it. `/login`
stays outside it. The selected project, suite, section, filters and page are
all in the query string and nowhere else: a pasted link opens the screen the
sender was looking at, and a reload keeps it.

The keyboard map is a pure function in `lib/keys.ts`: a keystroke plus the
statuses this instance has, the selection size and whether the run is
closed, in; an action out. That is where `3` is unbound, where `6`-`9`
resolve to the custom statuses in id order, and where a closed run turns a
status key into a refusal with a reason instead of a write that comes back
409 three keys later. Eleven tests cover it, none of them touching a DOM.

Failed and blocked open the result panel with the comment focused, because
`lib/db.ts` refuses either without one - the rule now lives in
`lib/format.ts` (`needsComment`) so the screen and the writer read the same
list. Passed and retest write straight through: the row changes on the
keystroke and rolls back with the server's message if the POST is refused.

Four server additions this needed, all measured:

- `listRunsWithProgress` - the run list with its bars in two queries
  instead of one summary request per row.
  `SEARCH tests USING COVERING INDEX idx_tests_run`, no temp B-tree, 2.5ms
  for a page of 25 runs over 50,000 tests.
- `listUsers` and `GET /api/users` - the names the run screens show instead
  of a user id, and the reassign picker. Active accounts only, columns
  listed by name so a password hash cannot leave the process.
  `SCAN users USING INDEX idx_users_email`, no temp B-tree.

- `projectOverview` and `GET /api/projects/:id` carrying an `overview` -
  the dashboard's open-run count and the status rollup across every test in
  the project, both SQL aggregates. `SEARCH runs USING COVERING INDEX
  idx_runs_project`, `SEARCH tests USING COVERING INDEX idx_tests_run`, then
  `USE TEMP B-TREE FOR GROUP BY`, 1.0ms over 10,000 tests. That temp B-tree
  is left alone deliberately: it holds one row per distinct status, not one
  per test, and a group across many run_ids cannot ride one index.
- `recentActivity` and `GET /api/projects/:id/activity` - the feed. This one
  needed an index: without it the planner scanned every result in the
  database through `idx_results_test` and sorted the lot (1.9ms at 5,000
  results, growing with the table rather than the page). Schema version 10
  adds `idx_results_recent ON results(created_on DESC, id DESC)`: no temp
  B-tree, 0.1ms, and the walk stops at the limit. Its ceiling is written
  above the index - a dormant project pays for the distance back to its last
  result, and the fix would need `project_id` denormalised onto `results`.

`GET /api/runs/:id` also carries `resultCount` now, so the delete
confirmation can name what it destroys before the button is pressed.

The dashboard renders no number without a sentence under it, which is the
one rule that screen has. The pass rate arrives inside the same
`RunProgress` a run uses, so it cannot be shown without its untested count,
and "nothing executed yet" renders as those words rather than as 0%.

Every stacked bar carries a labelled legend beside it. An imported custom
status brings its own colour from `statuses.color`, so hue alone cannot be
trusted to say which segment is which - the label does, and the colour is
the secondary cue.

**The import screen, and what it does not do.** The CSV path is a request:
upload, dry run, read the report, then press the second button to write.
The dry run reports what it would do inside a transaction that is rolled
back, and the three things the file cannot say - project, timezone, date
order - have no defaults in the form either, matching the route.

The API path has no form here on purpose. An instance import runs for
minutes to hours and resumes where it died, so it is `npm run migrate` and
the credentials stay in the environment; the screen prints the commands,
and polls `import_runs` every three seconds while one is live so its
progress and its report are readable from here. This is the deviation
`plan/04-testrail-migration.md` section 7 anticipated.

Deliberately not built in this cut, each because the cheap version is
honest and the expensive one has no caller yet:

- **No topbar search.** The only search that has an API is "cases in this
  suite", and that input belongs on the Cases screen where the results
  render. A project-wide search needs a route that does not exist.
- **No `app/ui.tsx`.** Two screens share three CSS classes, not three
  components. It arrives when the third screen wants the same wrapper.
- **No virtualised table.** The list pages in SQL at 25-100 rows, so there
  is nothing to virtualise; the cost of 50k cases in a suite is paid by
  `LIMIT`, not by the DOM.
- **No section collapse.** The tree is one pre-ordered CTE read and
  scrolls; a collapse state is one more thing to keep in the URL.
- **One page of projects, suites and users** in those switchers. Past a
  hundred of any of them, each wants a search box, and it is the same fix.
- **No last-result-time column** on the run detail list. It would need a
  `MAX(created_on)` per row on top of the test page; the panel's history
  already carries every timestamp for the row being looked at.
- **No attachment upload** on either screen. `POST /api/attachments` exists
  but nothing lists attachments back, so there is no honest way to show
  what is already attached - that route lands with the attachment work
  outstanding from phase 4.
- **Custom fields are read-only** on case detail, and a case whose `custom`
  bag holds a key with no row in `case_fields` has its step table
  read-only too, naming the keys. `custom` is one column: saving a step
  sends the whole bag, and the API refuses an undefined key. Offering an
  edit that is certain to be refused is worse than saying why. Editing
  arrives with the field-definition screen.
- **No run creation** in the UI. `POST /api/runs` takes the case set; the
  screen for choosing it belongs with the Cases multi-select, next cut.
- **No project or suite creation** in the UI either, for the same reason: an
  import or an API call makes them, and a form that creates a project
  nobody can then populate from the same screen is half a feature.
- **No credentials form** for the instance import; see above.
- **No `--resume` button.** Resuming is a CLI flag against a specific
  import run id, and the screen shows the id.

Verified against a seeded 140-case suite with nine nested sections: the
tree reads in one call with its per-section counts, `?priorityId=4` pages
at 25 (35 rows, page 2 holds 10), a bulk move of three cases reports
`{"changed":3}` and the section count moves with it, and a search for `%`
returns nothing rather than the whole table.

The run screens were verified against a second seeded project - 61 cases,
two runs, one result each of passed and failed. Every page the shell serves
answers 200. The run list reports `passRate 0.5, untested 59 of 61` on the
worked run and `passRate null, untested 61 of 61` on the untouched one, so
no bar borrows another run's results. A pass keystroke records
(`{"recorded":1}`), a fail with no comment is refused with
`A "Failed" result needs a comment`, the same fail with one is recorded,
`?status=3,5` returns 59 of 61, a closed run answers
`Run 2 ("Sprint 41 regression") is closed`, reopening as admin answers 200,
and saving a two-row step table on a migrated case rewrites `custom`
verbatim. A bag holding an undefined key answers
`No such custom field: mystery_field`, which is the case the read-only step
table above exists to keep off the screen.

The dashboard and import screens were verified against the same instance.
`GET /api/projects/1` answers `openRuns 2, totalRuns 2` with a rollup of
122 tests, 2 executed, 120 untested, `passRate 0.5`; the activity feed
returns the two recorded results newest-first with the author's name
resolved; a project with no results returns `[]` rather than a zero; and
`?limit=99999` returns 2 rows, because the bound is in `lib/db.ts` and not
in the caller.

The CSV import was driven end to end through the route the screen posts to.
A request with no timezone is refused with the reason rather than guessing.
A dry run reports 2 cases, 1 suite and 2 sections it would insert, names
`Nonsense Type` as an unmapped Type with its source id, and leaves the
database with one suite. The real import inserts all of it; a second
identical import reports `inserted 0, unchanged 2`. The import list shows
all three, with the dry run tagged `testrail-csv:dry-run`, and
`GET /api/migrate/2` returns a report with its durations and truncation
counters intact.

Review of the finished phase found eleven defects, all fixed in the same
turn. The three that would have cost somebody real work:

- The result panel was mounted once and reused, so its `useState` values
  survived a new intent. Open the panel on one test, press `j`, press `5`,
  type a failure reason, record - and the previous row's status went in,
  against the new test. The panel is keyed on what it is for now, so a new
  intent is a new form.
- A failed or blocked key with ten rows selected opened the panel on the
  cursor row, wrote one result and then cleared the selection: nine edits
  lost in silence, and the opposite of what `README.md` documents. The panel
  now carries the selection and records it through the run's bulk status
  route, which is also why a bulk record offers status and comment only -
  elapsed, defects, version and assignee are facts about one test.
- The global keydown handler exempted only fields, not buttons, so enter or
  space on a focused "Close run" was swallowed by the map. On a
  keyboard-first screen the keyboard could not reach the controls.

The rest: `countRunResults` was running on every run GET and therefore on
every status keystroke (5.3ms against 50,000 tests versus 1.5ms for the
summary) - it is asked for with `?resultCount=true` now, by the delete
confirmation, once; an empty suite list was shown as "this project has no
suites" while loading and swallowed a failed fetch; "Import for real" stayed
enabled after the project or timezone changed under a finished dry run; the
dashboard filtered open runs in JS over one page (now `isCompleted=false` in
SQL, with "showing 25 of 40" when the page is short); the activity route
answered 200 with an empty feed for a project id that does not exist (404
now); the import screen detected 403 by matching the word "role" in a message
(the thrown error carries the status now); switching project from `/runs/12`
kept the run id; and a `?page=` past the end rendered "101-100 of 100".

What a server cannot check: the keystroke-to-pixel path. `lib/keys.ts` is
tested, the routes behind it are verified, but nobody has pressed `j` in a
browser against this build.

This is a tool, not a landing page — but a tool with a point of view.
The Frontend aesthetics section of `../AGENTS.md` applies in full:
a deliberate typeface, a committed palette in CSS variables, a
background with some depth, no Inter and no purple-on-white.

Where taste meets the hot path, the hot path wins. Dense tables,
keyboard-first, and no animation that delays a click: motion belongs to
page load and state transitions, never between a keystroke and a
recorded result. Pick the type for legibility at small sizes in a
200-row table first, then for character.

Done when: a tester can run a 200-case run without touching the API.

## 2. Screens

**Cases** (`app/cases/`) — the screen people live in. Section tree on
the left, virtualised case table on the right. Tree from the single
recursive-CTE call. Table pages server-side at 50; it must stay fast at
50k cases in a suite, so no client-side filter over a full fetch.
Multi-select with shift-range, bulk move and bulk edit.

**Case detail** — fields by `template_id`, steps table for the steps
template, attachments, change history if cheap. Edit in place, save
explicit, no autosave surprise.

**Runs** (`app/runs/`) — the execution screen, and the hot path for a
human running tests. It must never require the mouse.

*Run list*: one row per run with a stacked status bar from
`runSummary`, the pass rate and the untested count side by side (never
the percentage alone — see phase 3 section 2), and open runs above
closed ones.

*Run detail*: the test list, filtered by status and assignee, paged
server-side. Each row is title, status pill, assignee, last result
time. The status pill colour comes from `statuses.color`, so an
imported custom status looks like itself without a code change.

The keyboard map, bound once in `lib/keys.ts` so it is testable:

```text
j / k, up / down   move the row cursor
1 2 4 5            set passed / blocked / retest / failed
6 7 8 9            custom statuses, in id order, when they exist
space              open the result panel on the cursor row
enter              record and jump to the next untested test
x                  toggle selection; shift+click selects a range
esc                clear the selection
/                  focus the filter
```

The status keys are TestRail's own ids, which is why `3` is unbound:
untested is not assignable. With a selection active a status key
applies to the whole selection through the bulk route; with none, to
the cursor row.

**Failed and blocked need a comment** (phase 3 section 3), so those two
keys open the result panel with the comment focused instead of writing
straight through. Passed and retest write immediately. The row shows
the new status at once and rolls back with an error if the POST fails —
no spinner between a keystroke and a visible result.

*Result panel*: status, comment, elapsed, defects, version, reassign,
attachment. Below it, that test's full result history newest-first,
which is the only change log there is.

*Closing a run* is offered in the header; deleting one is behind an
admin-only menu with the result count in the confirm prompt. A closed
run renders read-only — the status keys do nothing and say why, rather
than failing on the server after the keystroke.

**Dashboard** (`app/page.tsx`) — per project: open runs, pass rate,
untested count, recent activity. Every number gets a one-line
plain-language explanation. Numbers come from the phase 3 summary
functions, never recomputed here.

**Import** (`app/migrate/`) — a credentials form for the API path and a
file upload for the CSV path, dry-run preview table, start, live
progress polled from `import_runs`, final report with the unmapped and
skipped lists expandable. The CSV upload needs the project, timezone
and date order as explicit inputs (phase 4, 6.2); it does not offer
defaults for them. The report is the deliverable of
a migration; it gets a real screen, not a toast.

## 3. Data access

Client components fetch `/api/*`. No page imports `lib/db.ts`.
`lib/format.ts` is the only shared module.

Search inputs debounce at 300ms. Lists use the `PAGE_SIZES` from
`lib/format.ts`, no second pager implementation.

## 4. Tests

UI-only changes need no test. Anything that computes (a filter
predicate, a keyboard map, a status rollup helper) moves into `lib/`
and gets one there.

Specifically: `lib/keys.ts` maps a keystroke plus the current selection
to an action, with no DOM in it, and is tested that way — `5` with
three rows selected is a bulk failed, `3` is nothing, `1` on a closed
run is nothing.
